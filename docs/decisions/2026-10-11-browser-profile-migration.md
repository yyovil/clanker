# Checked adoption of reviewed browser profiles

## Finding

The persistent-profile architecture would otherwise create new empty personal profiles and leave existing working account sessions in legacy profiles. The read-only inventory under `.local/clanker-qa/findings/persistent-browser-principals/` found 34 profiles: 15 retained task profiles and 19 Managed Auth profiles. Six Managed Auth connections reported authenticated successful generations; this is provider metadata, not proof of current website behavior.

The exact reviewed proposal selects the existing Instamart profile `u7ttdj8bnpww44yc82bucilk` for workspace member `U0C688SF7DZ` and GitHub profile `wl2e91bdq8ud65pp4k3jg3ki` for `U0C6M6DMWAW`. The owner, connection, immutable credential-binding hash, proxy, allowed domains and deterministic principal key are recorded in `adoption-manifest-plan.json`. Its manifest fingerprint is `140903f87fec32f918aed6bafcab94aa6b638a8dcbae5232f823312fbbbbe74b`. No browser sessions were opened for this migration work, and no cookie or secret values were inspected or exported.

## Change

`ProfileMigration` accepts only an explicit metadata manifest. Fresh provider GETs must confirm the exact profile ID/name, owned authentication connection, routing policy and successful generation. The active-browser inventory must be empty. Local checks refuse existing canonical mappings, profile writers, pending owner forms and approvals, undelivered resumes, unresolved purchases, uncertain authentication/browser operations, conflicting profile claims and changed context files.

The first read-only preflight found five historical `create_unknown` flows with no connection ID on other legacy profiles. A narrow exception now proves separation from every reviewed donor: the complete legacy flow key must recompute from its exact context, account binding and proxy, and the profile name must match that key. The profile and account must differ from the donors. The request must be an expired waiting owner login, with no grant, principal, lease or connection, and must match current member identity, canonical request home, Slack source and exactly one historical auth selection. An isolated execution home additionally requires the exact persisted channel transfer, owner, canonical home and source. Missing, changed or ambiguous provenance still refuses migration. The exception retains these complete rows in the validation/commit CAS; it never edits or cancels them. Expiry only rules out a current human gate, not an unknown provider effect. The global empty active-browser check remains mandatory.

The first coordinated activation reached Slack on PID 53502 but correctly refused adoption before registering any principal: three old browser-context records still had uncertain state. A pure read-only invocation reproduced `_local` passing and `_files` refusing; ordinary Slack connectivity did not prove Vault availability. One exact browser, `cf17tyfgctdg1v8cn14x3h8l`, has provider-confirmed deletion and no attached profile. Two older anonymous launch markers have no browser ID. Empty provider history did not establish their dispatch outcomes.

The historical diagnostics rollout captured the owning code at `2026-10-08T07:56:45.709Z`: it wrote exactly the two-field marker and called `create_session(task_id)` without profile options. Its environment adapter exposed only the API key. The exact pinned provider (`475e97022b4015beda641028cedccbfa0333d7dea09995a1a9f99edd903a8683`) added a profile only for the hidden `KERNEL_PROFILE_NAME`, so these reviewed calls could not attach a donor profile. The captured Kernel output is a later-truncated excerpt, not a full source snapshot; the relevant complete dispatch and environment portions are retained. `historical-browser-separation-proof.json` binds those excerpt hashes, provider pin, exact isolated-transfer metadata, shared-task timeout log and context hashes. This proves profile separation, not that the old requests failed or never reached Kernel.

Optional operator-reviewed `browser_exclusions` bind the complete context-file hash, exact entry hash, context identity, thread-derived key and provenance artifact hash. They never infer anonymous status merely from a sparse entry. The anonymous case additionally requires the exact two-field footprint and no auth flow or selection in that context. The deleted case requires an exact owner claim, no attached profile/principal/lease and a fresh normal browser GET returning absence. Any extra, changed, missing or unused exclusion refuses migration. All original records remain untouched and quarantined; file CAS, current provider-empty checks and candidate validation remain required. The new proposed manifest is `adoption-manifest-with-browser-exclusions.json`, fingerprint `be459c022b558417f11361ed663ccf4cd034999c42bc6c65aa8ac9ecc4c5a6b8`. Its provenance fingerprint is `9f1415adbe7a3391e956d7ee420ed651696540425621fcc2a112cd890d192301`.

Both selected profiles are registered in one SQLite transaction. The transaction inserts their personal principals, tags the exact existing auth flows, records account bindings and adoption receipts, and retires only verified owner-local historical auth selections. It preserves flow keys, requests, provider connection IDs and generation evidence. It never copies a browser/CDP execution claim or owner approval. A later task must select its current account normally; the same historical DM root can then reuse the preserved connection. A second-donor failure rolls back the first donor too.

`ProfileRegistry.resolve` permits a legacy provider name only when its exact name and profile ID have a matching adoption receipt. Ordinary deterministic names and shared-profile rules remain unchanged. Completed receipts make repeated startup idempotent; this is historical migration evidence, not a new authentication claim.

`scripts/migrate-browser-profiles plan` reads the original proposal and current local routing metadata with SQLite `mode=ro`, then prints a reviewable manifest and fingerprint. It does not claim fresh provider validation. `apply --reviewed-sha256` only stages the exact reviewed manifest as a protected file at `.clanker-cloud/profile-adoption.json`; it does not write the live database, restart the gateway or call a provider mutation.

Actual adoption runs during the next QA-managed gateway restart, after Managed Auth construction and before the Vault service is published. It requires this process to own the gateway runtime lock, the matching live PID and the exact launch home; authority is checked again immediately before commit. Hermes replacement waits for the old process to exit and claims the PID/runtime lock before starting adapters. Thus an operator/import/test constructor cannot perform the migration. This is before private Vault admission, not a claim that Slack's socket is still disconnected.

Provider validation runs in a context-preserving worker thread, so bounded HTTP reads do not block Slack's event loop. Cancellation drains that worker before the membership task exits and never publishes a service from cancelled startup. The Hermes change is registered in `patches/hermes/clanker-profile-bootstrap-worker.patch`.

The second coordinated startup on PID 57732 refused at `local_quiescence`: Slack had scheduled the workspace policy before the gateway published its served-profile map. The unchanged private access check therefore correctly refused the migration's owner context. Before constructing Vault, workspace startup now awaits `serve_profile` for each distinct already-ready member profile. This uses the existing bounded asynchronous gateway reconciliation and waits for authoritative runner readiness; it does not fabricate a served route, weaken `assert_private`, or run onboarding/welcome work. Cancellation during this wait never starts the constructor, and the existing cancellation-drained worker behavior remains unchanged.

The authoritative `runtime/slack_workspace.py` and installed `hermes/gateway/slack_workspace.py` carry identical worker code. `scripts/apply-hermes-mods` applies the registered Hermes patch stack first, then verifies equality with the runtime source before copying it. Keeping both the authoritative source and the destination patch prevents that guard from rejecting the next setup or silently reverting the worker behavior.

Adoption refusal leaves the Vault service unavailable rather than silently starting fresh profiles. The protected outcome file records only status, manifest fingerprint, gateway PID and timestamp, with a fixed refusal description. Activation must check a fresh outcome for the new PID, both adoption receipts and Vault availability; a Slack-connected status alone is insufficient. Separate reviewed provisioning of the other two profiles runs afterward through its own module and manifest.

Refusal now also records a backend-selected phase enum (for example `browser_context_provenance` or `provider_profile_identity`), without exception text or provider payloads. This makes the stopped boundary visible without restarting to obtain a diagnostic. A local source/GET-only facade can invoke the actual `_prepare` path against SQLite `mode=ro`, current membership and credential metadata without constructing a production service or invoking apply/commit.

## Validation and limits

Canonical runner with zero retries: **114 passed across seven files** (`migration-final-green.log`). These cover 25 migration cases, two startup-worker contracts plus source/install parity, existing principal security and Managed Auth adoption/reuse contracts, and Slack membership behavior. Before the quiescence fix, four regressions failed with 17 passing: pending approval, approved-but-undelivered resume, expired undelivered resume, and an uncertain purchase attached to a separate cancelled/expired owner request. Both startup-worker tests failed before the worker change. The earlier new-suite attempts had fixture setup errors; they are preserved and are not counted as behavioral regressions.

The subsequent scoped-unknown correction reproduced **2 failed / 47 passed** before the change, then **72 passed across three files**, with zero retries (`migration-unknown-scope-red.log`, `migration-unknown-scope-green.log`). The updated migration file has 49 cases: two successful separate-profile shapes, 21 unsafe or ambiguous refusals and a changed-provenance-during-provider-GET regression supplement the prior 25. Independent peer review passed. A pure predicate check over the production SQLite database in `mode=ro` and current membership metadata confirmed the five actual historical records satisfy separation, including one exact isolated transfer (`migration-unknown-provenance.json`). This was not a service constructor, full migration preflight, provider absence check or resolution of the unknown effects; those records remain unresolved and unchanged.

The exact historical-browser exclusions then reproduced **2 failed / 60 passed** and passed **85 tests across three files** with zero retries (`migration-browser-exclusion-red.log`, `migration-browser-exclusion-green.log`). The migration suite now has 62 cases. New coverage requires explicit reviewed exclusions, preserves unknown/cleanup records, rejects changed file/entry/owner/thread/profile or auth context, missing claims, a still-present browser, an active provider browser and unused exclusions. Startup output also asserts the safe phase while retaining the private-error sentinel exclusion.

The actual `_prepare` path subsequently returned `ready` for both donors through read-only facades and fresh GETs (`migration-full-readonly-preflight.json`), ending at `provenance_recheck` with the new manifest fingerprint. It used the actual ManagedAuth evidence, credential metadata and connection validators without production service/store constructors or local/provider mutations. The facade's private access check covered static membership, home and DM identity but did not exercise the live `SlackWorkspaceMembership.route` served-profile boundary. That omission meant this was metadata/provider readiness, not full startup eligibility; the second startup exposed the ordering defect described above. Activation still repeats those checks under the gateway lock; this result alone is not an adoption receipt or website acceptance.

The served-profile ordering regression reproduced **2 failed / 3 passed** before the fix, then **5 passed** (`migration-served-startup-red.log`, `migration-served-startup-green.log`). It calls the actual migration owner-context builder, Vault private-access check, workspace route and gateway reconcile mixin. It verifies the constructor cannot run while real routes are pending, succeeds once the runner publishes them, and still refuses a subsequently removed route. Its cancellation variant never constructs or publishes Vault while awaiting readiness. Existing heartbeat, context propagation, cancellation-drain and authoritative-source parity contracts remain green.

Final related validation is **95 passed across four files**, zero retries (`migration-served-startup-related-green.log`): 5 startup, 62 migration, 20 auth-adoption and 8 workspace-membership cases. Independent peer review passed. The registered worker patch reverses and reapplies exactly, has one registration, and its installed output is byte-identical to the authoritative runtime source. This proves the local readiness repair; activation and fresh Vault/provider acceptance remain separate checks.

Tests verify atomic rollback, same-thread auth reuse without provider mutations, idempotence, changed claims during provider GET, conflicting owner metadata, unknown operations, exact manifest review, protected staging, gateway process authority, sanitized refusal output, heartbeat responsiveness, context propagation and cancellation draining.

The CLI preparation of the two-candidate manifest was read-only. No manifest was staged in production, no production migration was applied, and no gateway restart or live benchmark was performed by this lane. Adoption performs no profile create/delete, browser open/control, login, credential mutation, cookie export or message send. The separate provisioning stage may create exactly the other two reviewed profiles. Two adoptions plus two fresh profiles leave **36 provider profiles initially**, including 32 quarantined legacy profiles; literal four-profile cleanup remains a separate destructive review. Current website login, cart continuity and benchmark acceptance still require live verification after activation.
