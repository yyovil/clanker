## Change

`runtime/cloud_browser/profile_cleanup.py` coordinates an exact approved manifest, protected replacement-evidence references, local CAS, and a per-resource deletion journal. The absent-by-default hook in `VaultService.__init__` runs after adoption and provisioning, before publishing the Vault service. It requires the current gateway's runtime lock/PID/home and an unpublished Vault service. It creates no browser, profile, credential, or login and never transfers cookies.

The current private-routing and event behavior remains unchanged. A real served/authenticated Slack turn can still be admitted for ordinary conversation during startup; both seatbelt and the native browser handler call the owning `vault.service.binding()`, which refuses before any browser dispatch while Vault is unpublished. Worker cancellation continues to drain the constructor before gateway lifetime/lock release. No event barrier, private-ACL bypass, or new Hermes patch was added. The previously snapshotted Slack workspace files and patch-registration file remain unchanged by this cleanup.

`profile_cleanup_local.py` reads current membership and protected principal/account/item/grant rows, refuses profile leases and unresolved owner requests, approvals or purchases, and binds every target flow/context/claim to its exact owner and source context. Both owners being members does not authorize a substituted claim. A historical session ID appearing under different owner/context tuples is refused. Every profile must have concrete current local provenance. The private retirement journal snapshots exact inactive auth selections, target context entries and ownership claims; it removes only those rows/entries, prunes only thread selections pointing to removed sessions, and preserves unrelated threads, accounts, credentials, Vault items, grants, request/flow history, and all unknown records outside the target set. Historical browser references require fresh exact-ID absence before retirement. Atomic file replacement and SQLite transactions have restart-safe before/after CAS checks.

`profile_cleanup_provider.py` uses GET-only metadata before execution and exact-resource DELETE during guarded startup. Complete profile and exact-profile connection pagination is required. Connection policy, terminal generation, disabled health checks/automatic reauthentication, fresh global active-browser absence, and unchanged local authority are checked before dispatch. The owning response parser recognizes browser configuration; session/capability-shaped browser fields and external credential providers remain refusals. Credential lookups by their exact name bind the returned name and immutable ID into the approved metadata fingerprint. No credential values are read for comparison. All four Vault inventories must still use native Kernel items, and their metadata fingerprint is bound into the approval instead of being reseeded on restart.

Every DELETE is journaled as unknown before one dispatch. Timeout, process loss, or a lost response never authorizes another DELETE. A subsequent startup may only reconcile that exact resource with GET; a still-present unknown resource stops the batch. Same-name replacements, added connections, changed generations, lost authority, or changed credentials stop further deletion. Connection absence precedes profile deletion. Complete success requires a complete final inventory containing exactly the four approved canonical IDs. Partial receipts expose fixed reason codes and exact counts, not raw provider errors. Successful consumption is historical: later startups neither repeat deletion nor revalidate an old grant/lease snapshot.

2. Once current work is quiescent, run `plan --home <gateway-home> --source-plan <cleanup-plan.json> --acceptance <reviewed-acceptance.json> --output <new-cleanup-review.json>`. This performs only read-only SQLite and provider metadata work, then writes a new protected review file. `check --home <gateway-home> --review <cleanup-review.json>` refreshes that snapshot without mutation. 3. Present the exact 32 profile IDs and exact terminal connection IDs, the review digest, replacement evidence, and the loss risks for explicit destructive approval. Legacy cookies, carts, local storage, and previously working iCloud/Zepto/older GitHub sessions can be lost even though opaque saved credentials remain. 4. Only after that approval, `stage --home <gateway-home> --review <cleanup-review.json> --approved-sha256 <review-digest>` writes the protected manifest. Only the QA-managed idle restart may activate it. There is no standalone execute command, shell deletion loop, or manual stop/start path.
5. Read `status --home <gateway-home>` and require the new gateway PID/time, a complete receipt, restored Vault availability, and exactly four complete provider inventory entries. A partial/unknown result blocks Vault publication and requires exact reconciliation; it is not success.

### Restart health is not cleanup completion

The installed QA driver's `await_health()` defaults to 180 seconds and calls `gateway_healthy()`, which checks only the launched PID is alive, gateway state is `running`, and Slack is `connected` (`clanker_qa.py:835–836,891–900`). It does not inspect Vault readiness or cleanup receipts. The membership startup worker runs asynchronously, so `qa restart` can report `restarted` and mark source deployed while the bounded 1,800-second cleanup is still running. The QA driver's timeout is unchanged.

**Do not start any task based on `restarted` alone.** First require the protected cleanup outcome's exact approved manifest digest, `status: complete`, `remaining_profiles: 4`, current gateway PID, and a receipt timestamp after this boot. Then require this gateway's Vault `/health` to return HTTP 200 with `ready: true`, plus a complete provider inventory matching the four canonical IDs. A historical `previously_completed` receipt is only valid on an ordinary later boot and is not a fresh deletion result. No current outcome, pending cleanup, refusal, partial completion, or unavailable Vault means task admission remains on hold for the operator. Do not restart again just because the QA transport health check returned before cleanup finished.
