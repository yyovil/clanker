# Explicit fresh Managed Auth login

## Finding

The GitHub fresh-authentication run [r20261011-161312-sign-github-saved-a5d4](https://clanker-global.slack.com/archives/D0C6F49F2KD/p1791715392264529) signed out of its task browser and observed GitHub's sign-in form at 10:46:53 UTC on 11 October 2026. Authenticate, secure fill, and access-request calls subsequently returned the historical Managed Auth success. Hermes session: `20261011_161317_2a541914`; Kernel task browsers: `bexr4tsyerq2iq77iepz1d1z` and `eumzqzguqqb2ngzturta3hyr`.

The backend already refreshed the provider connection with GET. Its response still reported the previous login at 2026-10-10T18:55:30.835069Z, and the sanitized timeline contained no new login or reauth event. The defect was treating successful provider metadata as proof of current website authentication and offering no explicit fresh-login path. The final Slack response reported the mismatch truthfully. No authenticator challenge or submission was observed.

Normal browser stop verifies deletion and releases the thread selection while retaining the successful owned auth flow. The browser uses `save_changes=true`, so stopping may persist the logout into its profile, but subsequent selection still trusts the provider status. Stop then navigate cannot reliably start fresh authentication through the current path. Cookie deletion was not tested and would not bypass that branch by itself.

Kernel documents that health checks use a separate profile browser, not the agent's live browser. Its immediate login operation may finish quickly if the stored profile remains valid. [Official authentication documentation](https://www.kernel.sh/ai-library/agent-identity-how-to-authenticate-an-ai-browser-agent). The SDK provides POST `/auth/connections/{id}/login`, including stored-credential reauthentication; Clanker already wraps that operation. [Official SDK contract](https://raw.githubusercontent.com/kernel/kernel-python-sdk/main/src/kernel/resources/auth/connections.py).

## Change

`clanker_authenticate` accepts optional `fresh_login`, default false. Only a current authenticated owner's explicit fresh-login request can use it, through `Binding.owner_message`, not model arguments or gateway-added context. Authorization is closed over the entire request: every clause must be understood as unconditional fresh intent, related saved sign-in, scoped current-browser logout, saved-credential use, or credential/device/code-preservation instructions. The saved-sign-in clause accepts only `in using …` or `into <one site label> using …`; it has no free word slot that could swallow timing restrictions such as “in later” or “into GitHub tomorrow.” Unsupported compound targets conservatively refuse this exceptional path. An unknown clause refuses rather than discarding a condition, deferral, or withdrawal. Quoted, reported, stale-event and foreign-account requests are refused. Saved Vault-only accounts and invited accounts cannot use this Managed Auth path.

For a retained authenticated owned account, the existing renewal machinery reserves a different task-scoped connection/profile and reuses only the opaque saved credential reference. It checks the old immutable provider generation and current owner/account/origin/proxy binding before releasing only this thread's selection. The old flow, its profile, and sibling selections remain intact. Cancelled requests remain refused; the exact live GitHub donor was confirmed `authenticated` with a `resumed` request by a read-only metadata query.

A repeated call from the same owner event reuses its pending or completed generation. Unconfirmed create/login outcomes retain the existing refusal to replay. Normal reuse remains the default. Response guidance now distinguishes saved-profile success from live website acceptance. The login wrapper continues to disable recording and telemetry; no secrets pass through the model.

## Validation and limits

The initial behavior-contract suite failed 19 tests before implementation. The first implementation passed 22 focused cases and 326 checks across 14 auth/browser files. Independent review then found that colon suffixes and later clauses could withdraw permission without being respected. Ten added actual registered-tool → real ManagedAuth cases failed before that correction (24 other cases passed). Further withdrawal examples and two general harmless-scope examples were added for the closed-clause implementation.

The first whole-clause correction passed 41 fresh-auth cases and 86 relevant checks. A subsequent root review found that the sign-in target's arbitrary word slot still accepted deferred sign-in. Five added actual registered-tool → real-service cases failed before the narrower target grammar (43 cases passed), including both reported “tomorrow” and “later” requests. Two positive cases exercise the general bare sign-in and single-site forms.

The final focused suite has **48 passing fresh-auth cases**, including requester A → B → A isolation, original/alias/released selection, unchanged sibling bindings, owner-text provenance, cancellation and provider drift, duplicate dispatch, uncertain create/login, and actual registered-tool no-dispatch checks for deferred/conditional/withdrawn permission. Exact live wording and generic scoped-logout/credential-preservation requests pass. Independent review of the final target grammar and real-service regressions passed, including six additional pure-parser checks.

After the target-grammar correction, canonical `scripts/run_tests.sh --file-retries 0` passed **93 tests across five files, zero failures and zero retries**: fresh login, reuse, reuse security, owner request text, and explicit public-update destination. The earlier 326- and 86-check runs predate this correction and remain earlier regression evidence, not final reruns. Canonical logs and snapshots are under `.local/clanker-qa/findings/managed-auth-stale-authenticated-after-logout/`: `fresh-red.log`, `fresh-regression.log`, `fresh-authority-red.log`, `fresh-authority-green.log`, `fresh-signin-timing-red.log`, and `fresh-signin-timing-green.log`. Prior dirty work was preserved.

This is locally verified code, pending coordinator-controlled activation while idle. No provider mutation, fresh live run, restart, cookie deletion, credential/seed change, manual code generation/injection, or recording was performed during remediation. A fresh profile and provider success are not TOTP acceptance evidence. The later live run must observe an actual challenge, autonomous stored-authenticator handling, authenticated owner afterward, and the original repository followups. **Live autonomous TOTP and benchmark completion remain unverified.**
