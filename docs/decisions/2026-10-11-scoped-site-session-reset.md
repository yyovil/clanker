# Exact-site session reset before fresh Managed Auth

Status: implemented locally; live deployment and GitHub challenge verification pending.
Finding: `scoped-site-session-reset`.

## Finding

The owner authorized clearing GitHub cookies in their current browser to test a genuinely fresh login. The available native `cookies clear` command clears all cookies, while `fresh_login=true` renews a Managed Auth generation without removing a pre-existing site session. Neither alone establishes that a new authenticator challenge occurred.

## Change

`clanker_authenticate` now accepts `reset_site=true` only with `fresh_login=true` and an explicit owned saved handle. The entire current Slack request must express fresh sign-in and a complete exact-host reset instruction, such as “I want a fresh login. Clear cookies and site data for github.com in this browser only. Use my saved login and authenticator automatically.” Quoted, conditional, future, wrong-host and synthetic-resume instructions do not authorize this exception. The existing fresh-login parser is unchanged for ordinary calls.

The reset broker requires an existing Managed Auth connection, the currently selected personal principal and matching owned credential binding. Shared profiles and granted credentials are refused. Current browser ownership, provider profile attachment with save-changes enabled, CDP claims and the native active-document marker are checked. There must be exactly one page in that browser context at the saved HTTPS origin. No other browser or profile is opened. Unfinished private forms, owner approvals, undelivered resumes or uncertain purchases tied to this profile, or whose profile provenance is ambiguous, block reset even when their expiry has passed. A narrow exception preserves an expired legacy create-unknown request only when its exact linked flow has no connection, principal or lease, names a deterministic different legacy profile and different account, and matches the stored team/owner/home/origin/handle/source-thread identity. Such a writer cannot mutate the selected profile. The old request and unknown flow remain unchanged; expiry alone is never evidence of a resolved provider effect.

The trusted backend checks every cookie selector before mutation. It disables scripts, stops loading, and clears exact-origin session storage while its frame remains available; then it leaves the inspected document for `about:blank` and clears local storage, IndexedDB, cache storage and service workers for only the saved origin. Chromium resolves DOM storage through a live matching frame, so session storage clearing must precede navigation. Navigation acknowledgment is followed by bounded read-only target metadata observation until the same page commits `about:blank`; the broker never repeats navigation or evaluates page scripts after disabling them. Unexpected navigation or failure to observe commitment stops the reset. Cookie deletion enumerates the verified browser context internally and matches the exact saved hostname or its dot-prefixed domain cookie. It deletes by name, domain, path and exact partition key. It never deletes sibling subdomain cookies, uses `clearBrowserCookies`, or sends `all` to storage clearing. Unknown/opaque partition selectors are refused, and an unsupported partition deletion never falls back to a broader deletion. Cookie names, values and storage contents are not returned or persisted in receipts.

This split is necessary because Chromium's origin storage clearing does not provide the required cookie-domain semantics. The current [Chromium cookie filter](https://raw.githubusercontent.com/chromium/chromium/main/content/browser/devtools/protocol/network_handler.cc) matches domain/path and partition identity exactly; an omitted partition key selects unpartitioned cookies. [CDP Storage](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Storage.pdl) provides context-scoped enumeration and exact-origin storage clearing. Runtime responses remain authoritative: unsupported protocol behavior stops the operation rather than widening it.

The durable reset ledger stores only opaque operation/owner/lease/connection identities and phases. It reserves `resetting` before side effects. An uncertain reset or close records `unknown`; neither the same event nor a later event repeats the mutation. After exact provider closure is confirmed, a typed, non-model-constructible `VerifiedBrowserClosure` permits the registry's atomic browser-to-auth lease handoff. The principal is never unlocked between browser save and authentication. The existing Managed Auth connection/profile is renewed once.

A crash after verified close can re-confirm the same browser's absence without replaying the reset. A crash after the lease handoff but before the receipt write reconciles only the exact intended auth writer, principal, owner, home, thread and connection. Stale browser cleanup cannot release the new auth lease. No successful provider login result is treated as proof of a TOTP challenge; the independent observer must establish that separately.

## Validation and limits

Validation uses the canonical `hermes/scripts/run_tests.sh` runner. The initial regression failed with the missing broker; further regressions reproduced pending-gate, session-frame ordering, navigation-commit and distinct legacy-profile problems before correction. The focused broker suite has 55 passing cases, including real Kernel profile/lease state plus actual Managed Auth renewal with provider doubles. The seven-file suite passed198 checks; the final three added contract cases brought unique coverage to201 (55 reset +146 related). It covers reset, lease handoff, fresh authentication, persistent identities, dispatch, browser ownership and reuse security. Evidence: `.local/clanker-qa/findings/scoped-site-session-reset/reset-final-green.log` and `reset-frozen-contract-green.log`. Independent source review passed. The old browser test fixture now supplies the registered personal principal instead of an unmapped legacy task profile, preserving its 27 ownership/lifecycle assertions under `persistent-browser-principals`. Protocol tests verify scoped calls, partition preservation, pre-mutation refusal and no broad fallback; crash tests verify both handoff receipt windows. No production browser reset or sign-in was performed. One initial combined fixture omitted its no-I/O vault stub and attempted a read with the hardcoded invalid fixture key (401); the fixture now explicitly forbids live vault transport.

Limits: this is a local verified contract, not live proof that GitHub presents a challenge or that Kernel supplies an authenticator automatically. Site reset intentionally destroys only the authorized site's local session and may discard that site's unsaved page state. It does not sign out other devices or change saved credentials. Unsupported browser protocol behavior or an uncertain provider outcome requires reconciliation; the broker will not guess or retry a reset.

Primary session-frame implementation: [Chromium DOM storage agent](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/modules/storage/inspector_dom_storage_agent.cc). Kernel documents profile writes on browser termination with `save_changes=true`; this broker verifies the existing writable attachment and exact remote closure before the atomic handoff. Live provider persistence remains part of acceptance verification.

Verified complete opening for the GitHub acceptance run (ordinary scenario follow-ups remain separate):

> Sign me into GitHub using my saved login and authenticator. I need a fresh sign-in this time. Clear cookies and site data for github.com in this browser only. Don’t ask me for a code or sign me out on other devices. Don’t change security settings or saved credentials.
